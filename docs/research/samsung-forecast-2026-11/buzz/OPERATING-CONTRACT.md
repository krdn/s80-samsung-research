# S80 연구팀 운영 계약

대상은 삼성전자005930 방향80% 연구 문서의 지속 개선이다. 기준 문서는 `docs/research/samsung-direction-80-research-2026-11.md`, 역할·설정·현재 상태는 [TEAM.json](TEAM.json)이다. 전체 제품 개발·자동 주문·데이터 인증을 포함하지 않는다.

## 전용 역할과 이력

| Buzz 이름 | 이전 참여 | 맡는 일·저장 모델 |
|---|---|---|
| S80-총괄 | 주 책임자t4r | 조사 분배·토론·통합·버전·검사, Codex gpt-6.1-sol (UI 저장) |
| S80-R1-데이터 | R1t4s | API·시점·이용권, 같은 Codex 설정 |
| S80-R2-퀀트 | R2t4t | 논문·알고리즘·통계, 같은 Codex 설정 |
| S80-R3-산업 | R3t4v | 증권·반도체·미래 시나리오, 같은 Codex 설정 |
| S80-외부검토 | Claude Opus5.5 검토 실행 | 읽기 전용 최종 검토, Claude Opus5.5 (UI 별칭 opus) |

모델명은 Buzz UI에 저장한 선택이다. 제공자 반환 모델·effort는 별도 증거가 없으면 미검증이다. xhigh/high는 초기 제안이며 별도 override를 적용하지 않았다.

새 Buzz 신원이 기존 Herdr 세션 그 자체는 아니다. 기존 파일·결정·실패·검증 한계를 인계해 같은 역할을 지속한다. 모든 이름에 S80-을 붙여 다른 업무와 구별한다. 기존 Codex-buzz·Claude-buzz 등 범용 에이전트의 이름·프롬프트·권한을 변경하지 않는다.

## 주기와 시작 조건

- 기본: 매주 **화·금18:30 Asia/Seoul**. Buzz cron은 UTC이므로 `0 30 9 * * TUE,FRI *`이다.
- 매회 최근 공식 API/약관·기업 공시·원논문·반대 근거의 변경을 조사한다. 월 첫 실행에는 전체 방법론·출처 신선도·반복 실패도 점검한다.
- 실행당 전문 작업자 동시2명, 새 run 동시1개. 같은 trigger event_id는1회만 처리한다. 기존 활성 run이 있으면 건너뛰고 원인을 기록한다.
- run 시작 시90분의 운영 기한을 기록한다. 후속 회신·다음 예약 때 기한을 넘은 실행을 발견하면 BLOCKED_TIMEOUT으로 종결하고 누락 역할·단계·이유를1회 알린다. 미완료 worker 상태를 모르면 새 run을 겹쳐 실행하지 않는다. 기한 뒤 도착한 옛 회신으로 이미 닫은 run을 승격하지 않는다. 승인된 재개는 새run과새입력해시를 사용한다.
- 예약은 초기 비활성 등록 후,5개 전용 신원·멤버십·UI 모델 선택·실응답·시범 산출물 검사를 거쳐 소유자Gon 신원으로 활성화했다. 실제 반환 모델은 별도 미검증으로 유지한다. 현재 서버 재조회 근거는 TEAM.json과 evidence/workflow-active.json이다. 수신·파일 접근 실패를 성공으로 간주하지 않는다.
- 호스트의 Buzz Desktop/에이전트와 네트워크가 실행 중이어야 한다. 재부팅·로그아웃 후 자동 재개는 실제 확인 전 미검증이다. 기존 상주 서비스나 계정을 임의 변경하지 않는다.

## 실행 흐름

1. 총괄은 `buzz/STOP`이 있으면 시작하지 않는다. 실제 요청 event_id로 run_id를 만들고 입력 파일 목록·SHA·90분 기한을 manifest에 저장한다. 원래 파일을 `versions/<run_id>.before.md`에 복사하고 현재 내용이 바뀌면 덮어쓰지 않는다. 상태 전이는 짧은 flock 안에서 재확인·기록하며, 요청 전 `*_REQUESTED`를 저장하고 대기 중에는 잠금을 해제한다.
2. R1/R2가 독립 조사한다. 각 역할은 run 폴더의 자기 결과만 쓴다. 총괄은 WAITING 상태를 저장하고 회신을 기다린다. 장시간 polling·무한 메시지를 만들지 않는다.
3. R3가 산업 조사와 반론을 작성한다. R1/R2가 서로와R3의 핵심 가정을1회 교차검토하고 질문에 직접 답한다. R3는 `industry-answer` 단계에서 질문에 직접 답한다. 합의되지 않은 쟁점도 보존한다. 독립 조사는 역할당15분, 교차검토·응답은 각10분, 후보·검사·외부검토는 합계30분 이내를 운영 목표로 삼는다. 각 역할은 요청된 단계마다 한 번만 응답하며 총괄은 자신을 멘션하지 않는다.
4. 총괄은 근거가 바뀐 부분만 후보 문서에 반영한다. 새 증거가 없으면 NO_CHANGE로 종료할 수 있다. 문서 길이·변경 수를 성과로 삼지 않는다.
5. 후보 문서 검사를 먼저 수행하고 외부검토가 정확한 후보 SHA·diff·토론·수치·검사 결과를 확인한다. PASS 전 canonical 교체 금지. 필요하면 수정분1회만 재확인하며 `external-review-1.md`와 `external-review-2.md`, 대응하는 `review-verdict-<n>.json`을 덮어쓰지 않고 보존한다. 해시·대상이 다르면 BLOCKED다.
6. 총괄만 canonical 문서를 갱신한다. `versions/<run_id>.before.md`·`versions/<run_id>.after.md`, `runs/<run_id>/manifest.json`, `changes.md`에 전후SHA·채택/기각·출처·검사·미검증을 연결한다. 총괄은 이 파일들과 TEAM.json·STOP을 관리할 수 있다. 전문 역할은 자기 결과와 `bootstrap-<role>.md`만 쓴다. 원본 역할 연구·과거 예측·평가를 덮어쓰지 않는다.
7. 채널에 결과1회와 경로·SHA·핵심 변화·실패/보류를 게시한다. DONE·감사·과거 회신에 새 작업을 자동 생성하지 않는다.

manifest에는 `thread_root_event_id`도 저장한다. 총괄의 요청과 전문 역할의 회신은 해당 run의 원래 시작 이벤트를 `--reply-to`로 명시한다. 최신 수신 메시지의 기본 회신 대상을 그대로 사용하지 않는다. 다른 run·bootstrap의 회신이 섞이면 자동 승격하지 않고 요청ID·root·phase·입력 SHA로 분리한다.

TEAM.json·운영 계약을 입력 SHA로 전달한 뒤에는 해당 작업자가 모두 종료할 때까지 수정하지 않는다. 진행 상태는 run의 manifest와 별도 evidence 파일에만 기록한다. 구성 변경이 필요하면 기존 역할을 종결하고 새 입력·새 run으로 재개한다. 복원 뒤에도 이미 차단된 phase를 같은 이름으로 다시 실행하지 않는다.

## 완료 조건과 중단

- API·논문·산업 주장의 발행/확인 시각·원문·적용 범위가 있고 숫자는 재계산 가능해야 한다.
- 80% 달성 근거가 없으면 그 표시를 유지한다. 확률·구간 포함률·선택 적중률·수익률로 바꾸지 않는다.
- 자료 이용권·PIT·정정·보합·누락·미평가·거래 캘린더·lockbox 자격을 보존한다. 최신LLM으로과거를재생한성적을전향성적으로쓰지않는다.
- 미해결 주요 결함·권한 거절·원문 부재·해시 충돌·중복 run이면 현행을 보존하고 BLOCKED/REVISE로 보고한다.
- 새 예약은 활성 run을 먼저 점검한다. 타임아웃이 확인된 경우 완료로 꾸미거나 계속 WAITING으로 숨기지 않고 차단 상태를 보고한다. 이 계약은 시간 제한을 자동 강제하는 별도 프로세스 구현이 아니므로 실제 지연·재개는 시범과 운영에서 확인한다.
- 일시 네트워크 오류만1회 재시도한다. 인증/소유자 오류는 다른 키·관리 JSON 수정으로 우회하지 않는다. 정기 작업은 유료 데이터·계정·배포·Git push·자동 매매 권한을 추가하지 않는다.
- 사용자가 전용 채널에서 중지하면 총괄이 `buzz/STOP`에 요청ID·시각을 저장하고 현재 run 상태와 미완료를 기록한다. 명시적인 재개 요청 전에는 STOP을 지우거나 새 run을 시작하지 않는다. 예약 자체는 [중지 YAML](workflow-disabled.yaml)을 소유자 CLI로 적용해야 하며, 일반 에이전트가 다른 소유자의 Workflow를 강제 변경하지 않는다.

## 안전한 재개와 수동 명령

모두 기존 `buzz-gon` 인증 실행기를 사용한다. 비밀값을 인수·파일·로그로 복사하지 않는다.

```sh
buzz-gon channels members --channel 11c1ea3c-c9c1-49fa-ae2c-bced8d7616b5
buzz-gon users get --name S80-총괄 --owner me
```

Workflow ID는 TEAM.json의 실제 값을 사용한다. 활성화 전5명 멤버십, 같은 채널/스레드의 요청·서명 회신, 실제 산출물 경로·SHA와 검토 결과를 확인한다. `workflows runs`의 빈 배열은 성공·실패 부재의 증거가 아니므로 메시지·artifact를 함께 확인한다. 예약 메시지 접수와 문서 갱신 완료를 구분한다.


## 채널에서 운영하기

전용 채널에서 소유자 Gon이 총괄을 멘션한다.

- `@S80-총괄 현재 진행 상태와 마지막 결과를 알려줘`: 새 run 없이 상태만 확인한다.
- `@S80-총괄 정기 연구를 중지해`: STOP을 저장하고 진행 중 단계·미완료를 기록한다. 이미 처리 중인 외부 호출의 즉시 취소는 보장하지 않는다.
- `@S80-총괄 중지한 연구를 재개해`: 기존 작업자 종료·해시·차단 원인을 확인한 뒤 명시적으로 STOP을 제거하고 새 run으로 재개한다.
- `@S80-총괄 [S80-CYCLE] 지금 연구를 갱신해`: 활성 run이 없고 STOP도 없을 때 수동 연구를 시작한다.

예약 메시지 자체를 멈추거나 다시 켤 때는 소유자 실행기를 사용한다.

```sh
buzz-gon workflows update --channel 11c1ea3c-c9c1-49fa-ae2c-bced8d7616b5 --workflow 05956bbb-d982-47c1-9297-1aaa4b35a7bc --yaml - < docs/research/samsung-forecast-2026-11/buzz/workflow-disabled.yaml
buzz-gon workflows update --channel 11c1ea3c-c9c1-49fa-ae2c-bced8d7616b5 --workflow 05956bbb-d982-47c1-9297-1aaa4b35a7bc --yaml - < docs/research/samsung-forecast-2026-11/buzz/workflow-ready.yaml
```

둘 중 원하는 명령 하나만 프로젝트 폴더에서 실행하고 `workflows get`으로 상태를 다시 확인한다. 예약 활성화는 STOP 해제를 뜻하지 않는다. 운영 검증과 현재 상태의 근거는 [TEAM.json](TEAM.json)과 [시범 폴더](runs/bootstrap-20261110/)에 보존한다.
