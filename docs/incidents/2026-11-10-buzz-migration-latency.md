# Buzz 연구팀 이전 지연 분석

이번 지연의 큰 원인은 실행 경로를 늦게 확정한 것, 설정 이전에 비해 검증 범위를 크게 만든 것, 운영 상태를 동결 입력에 써서 재작업을 만든 것이다. Buzz의 GUI 제약과 실제 충돌도 있었지만, 이를 처리하는 내 절차가 시간을 더 늘렸다.

## 지연 원인과 책임

### 1. 실행 방법을 확정하기 전에 사용자에게 작업을 돌렸다 — 가장 먼저 고칠 부분

`draft-create`의 `accepted:true, saved:false`는 Desktop에 초안을 보냈다는 뜻이었다. 실행 인스턴스 생성은 아니었다. 그런데 저장·Run을 사용자에게 여러 번 요청했고, 사용자가 Run을 찾지 못한 뒤에야 직접 실행 경로를 조사했다. 사용자는 이미 구성을 요청했고 결국 “너가 직접 실행해”라고 다시 지시해야 했다.

초안 저장과 런타임 시작의 상태 모델을 먼저 확인했어야 한다. 실제 성공 경로는 New agent → Add agent였고, 확인한 UI 소스는 `definition_start`로 인스턴스 생성과 시작을 연결했다. 실행 중 프로필에는 Stop·Restart가 표시됐다. 이 경로를 먼저 찾았다면 설명·사용자 왕복·중복 초안 상태 확인을 줄일 수 있었다. 이는 권한 부족 때문이 아니라 기능 경계를 잘못 이해한 문제다.

근거: `evidence/draft-coordinator.json`, `draft-data.json`, 이 대화의 사용자 답변 및 Native Add agent 실행 기록.

### 2. 현재 환경보다 과거 도구 경로를 앞세웠다

현재 환경은 Herdr였는데 Orca 경로를 시도했다. 사용자의 정정 뒤 임시 Orca 런타임을 종료했다. 과거 메모리의 도구 안내를 현재 환경 선택으로 그대로 이어간 판단이 잘못됐다. 메모리는 후보를 찾는 데만 사용하고, 현재 사용자 환경을 첫 분기 조건으로 삼아야 했다.

이후에도 일반 Python의 gi 부재, Text 메서드 혼동, EditableText 미지원, 포커스 미확인, 다중 모니터 좌표 불일치 등을 순차적으로 겪었다. 접근성 action이 true를 반환해도 입력·메뉴 변경이 완료된 것은 아니었다. 실제 값 읽기와 GUI 전환 완료를 한 번에 검증하는 작은 사전 시험이 없어서 실패 원인을 늦게 좁혔다.

최종적으로 `/usr/bin/python3 -E`의 AT-SPI, 의미 기반 컨트롤 선택, 실제 창 활성화 확인, 클립보드 입력과 정확한 읽기 검증이 작동했다. 메뉴는 팝업까지 검색하고 스크롤·비동기 화면 전환을 처리해야 했다. 이 성공 조합을 먼저 좁힌 후 반복 생성에 적용했어야 한다.

### 3. 반복 실행기가 준비된 시점이 늦었다

초반에는 입력·클릭·전체 트리 출력·다시 조회를 잘게 반복했다. 긴 트리가 여러 번 잘렸고, 동일한 상태를 찾기 위한 추가 호출이 생겼다. 나중에는 같은 폼을 묶어 처리해 R2/R3 생성이 빨라졌다.

임시 `/tmp/s80-buzz-ui.py`는 검증된 출발점이지만 재사용 가능한 제품 수준 도구는 아니다. PID와 창 ID를 하드코딩했고, 종료된 접근성 객체·저장 후 전환 지연 때문에 실패했다. 다음에는 실행 시 PID/창을 새로 찾고, 저장 후 “폼이 닫힘 + 정확한 공개 신원 확인”을 기다려야 한다. 고정 sleep이나 action 성공값만으로 다음 폼에 진입하면 안 된다.

### 4. 간단한 연결 검사를 여러 번의 긴 LLM 작업으로 만들었다

5개 bootstrap은 각 역할이 신원·계약·원문 기록·모델 한계 등을 읽고 Markdown을 작성하도록 했다. 그 뒤 별도 quant probe, 후보 문서 작성, 외부검토, 총괄 통합을 추가했다. 실제 통신 검증은 필요했지만, 연결 확인에 필요한 것보다 문서 작업이 많았다.

Native transcript의 Usage 표시도 약5.7만~14.9만 토큰 규모였다. 이는 화면의 세션 컨텍스트 표시이며 과금 토큰이나 각 응답의 생성량이 아니다. 단순 검사에서 스킬·메모리·계약을 반복 읽는 모습은 관찰했다. 컨텍스트가 추론 지연에 기여했을 가능성은 있지만, 제공자 대기시간·토큰별 처리시간을 계측하지 않아 비중을 단정하지 않는다. 모델을 무단으로 바꾸는 것보다 입력과 검사 범위를 먼저 줄이는 것이 맞다.

### 5. 자동 멘션과 스레드 선택을 통제하지 못했다

전문 역할에게 보낸 소유자 요청 본문에 총괄 멘션도 들어가서 총괄이 여러 메시지를 받았다. 채널 단위 컨텍스트에서 최신 수신 메시지의 회신 대상으로 옮겨가 초기 bootstrap 회신 스레드가 달라졌다. 같은 내용의 완료 보고도 추가됐다.

이후 run의 root ID를 저장하고 `--reply-to`를 명시해 고쳤다. 후속 team-probe·외부검토는 root 일치를 확인했다. 이 규칙은 처음부터 있어야 했다. 의도한 수신자 이외의 이름에는 @를 붙이지 않고, 요청 접수 결과의 mention_pubkeys도 확인해야 한다.

근거: `evidence/pilot-routing-correction.json`, `runs/bootstrap-20261110/pilot-routing-evidence.json`, `pilot-result.md`.

### 6. 내가 실행 중 입력을 변경해 실제 재작업을 만들었다

총괄이 TEAM SHA를 고정해 작업자에게 전달한 뒤, 내가 진행 상태를 TEAM에 추가했다. 두 역할은 해시 불일치를 발견하고 정상적으로 BLOCKED 처리했다. 차단 장치는 올바르게 작동했다. 문제는 내 상태 기록 위치와 변경 시점이었다.

TEAM 원래 바이트를 복원하고 진행 상태를 별도 evidence로 옮겼다. 이전 run과 작업자 종료를 확인한 후 새 run으로 재개했다. 13:03:08에 새 요청 두 개가 발행됐고 두 역할 모두 입력10개 일치와 실제 조사 진행을 확인했다. 약12:58~13:03의 복구 경과는 관찰되지만, 이를 순수 추가 손실5분으로 단정할 대조 실행은 없다.

근거: `evidence/first-refresh-input-mismatch.json`, `first-refresh-recovery-request.json`, `recovery-frozen-inputs.json`, `recovery-specialist-requests.json`, `first-refresh-live.json`.

### 7. Buzz 자체 충돌과 조회 제약도 있었다

12:36:02 Desktop의 segmentation fault를 사용자 journal에서 확인했다. 외부검토 생성 폼을 다시 입력해야 했다. 충돌은 실제 환경 요인이지만 원인 분석·재현은 수행하지 않았다. 내가 사용한 접근성 조작이 충돌을 유발했는지도 입증되지 않았다.

또한 workflows runs는 빈 배열을 반환했고, 실제 실행은 Workflow 메시지·수신·산출물로 확인해야 했다. Canvas get은 format=json을 지정해도 Markdown 본문을 반환해 최종 JSON 검사도 한 번 실패했다. 둘 다 도구 반환 형식을 먼저 한 번 확인하고 재사용했다면 마지막 단계의 시행착오를 줄일 수 있었다.

근거: `evidence/desktop-crash.txt`, `first-refresh-workflow-runs.json`, `canvas-active-readback.md`와 이 대화의 파싱 오류 기록.

## 다음번 빠른 실행 절차

**설정·동결·검증을 한 번씩 수행하고, 통신 검사에 실제 첫 작업을 재사용한다.** 다음 절차는 제안이며 이번에 새 자동화 프로그램을 구현하거나 성능 측정한 결과가 아니다.

1. **환경과 완료 기준 확정, 목표2분.** Herdr/호스트/기존 Buzz 확인. 완료 기준은 채널,5개 신원·실행, 멤버십, 역할별 최소 응답, 팀 왕복, 활성 예약이다. 연구 전체 결과를 기다리는 단계는 별도 진행 상태로 보여준다.
2. **컨트롤 하나로 사전 시험, 목표2분.** 이름 입력→정확 읽기→메뉴 선택→상태 확인을 한 폼에서 검증한다. 같은 실패를 두 번 반복하면 다른 좌표를 계속 시도하지 말고 API·컨트롤 지원·포커스를 진단한다. 사용자에게 클릭을 맡기는 것은 실제로 제어할 수 없는 인증/소유자 전용 단계로 확인됐을 때만 한다.
3. **정의·신원·채널 구성, 목표4~7분.** 현재 지원되는 공식 CLI/API로 가능한 부분을 묶는다. 생성·시작 API가 없으면 검증된 GUI 경로로 순서대로 생성한다. 저장 이벤트와 정확한 owned profile을 확인한 뒤 다음 역할로 간다. 이미 존재하는 이름·공개키를 재사용해 중복 생성을 막는다.
4. **설정 동결, 목표1분.** 모든 신원을 먼저 등록하고 TEAM·계약의 SHA를 확정한다. 상태는 run/manifest 또는 별도 status 파일에 쓴다. 활성 작업자 입력 파일에 완료 표시를 추가하지 않는다. root와 phase를 요청 전에 정한다.
5. **최소 연결 검사, 목표3~5분.** 역할별 요청은 역할ID·run·phase·입력1개SHA·출력1개·고정root만 담는다. 검증 전용 단계에서는 광범위 메모리 검색·원문 재조사·설정 전체 감사를 요구하지 않는다. 각 역할은 작은 receipt 하나를 쓰고 한 번 회신한다. 동시2명 제한은 유지한다. 팀 왕복은 첫 실제 연구 요청/회신으로 검증해 같은 일을 probe로 재실행하지 않는다.
6. **일정과 실제 전달 확인, 목표2~4분.** 소유자 신원으로 예약을 켜고 재조회한다. 동일 Workflow의 수동 시작 메시지와 실제 수신을 확인한다. 첫 정기 시각의 발생과 장기 문서 품질은 그때의 실행 기록으로 검증한다. 통신 성공을 성능80%로 확대하지 않는다.

재사용 경로가 작동하고 모델 대기·충돌이 없는 경우 **15~25분을 다음 실행의 목표 범위**로 제안한다. 실제 측정된 보장은 아니다. 신규 하네스·인증·새 권한·충돌 진단이 필요하면 별도 시간을 기록한다. 단계별 목표는 겹침과 편차가 있어 단순 합계로 상한을 보장하지 않는다.

| P0 | 고정 root·명시 수신자·phase당1회 | 잘못된 root0, 우발적 멘션0, 중복 요청0 |
| P1 | 역할별 짧은 receipt와 공통 검증 한 번 | 각 역할 실제 회신·SHA를 유지하며 문서/검사 중복 감소 |
| P1 | 단계 시작·종료·대기 원인을 자동 기록 | GUI/서버/모델/사용자/재작업 시간을 구분할 수 있는 다음 실행 비교표 |
| P2 | Buzz의 공식 생성·시작·상태 API 제공 여부 확인 및 가능하면 제품 기능으로 지원 | 문서화된 API와 실제 시작·회신 증거. 현재 없는 CLI 옵션을 있다고 가정하지 않음 |

이번 분석은 실행기 구현·Buzz 소스 변경·모델 교체·전역 메모리 수정까지 포함하지 않는다. 현재 연구가 읽는 TEAM·운영 계약·에이전트 지침도 변경하지 않았다. 이 문서는 별도 사고 기록으로 저장했다.
